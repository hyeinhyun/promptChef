# speckit.constitution

작성일: 2025-11-04
범위: PromptChef 프로젝트 전반의 코드 품질, 테스트 표준, 사용자 경험 일관성, 성능 요구사항

---

## 1. 간단 계약 (Contract)
- 입력: PromptChef 코드베이스 및 운영 요구(기능/비기능 요구사항).
- 출력: 적용 가능한 원칙 집합(코드 품질, 테스트, UX, 성능)과 계량 가능한 검사 항목.
- 성공 기준: 각 원칙에 대해 CI에서 자동으로 체크 가능한 최소 1개 검사 또는 PR 체크리스트가 제안되어야 함.

---

## 2. 프로젝트 컨텍스트 (Sketch 기반 요약)
PromptChef는 한국 비즈니스 맥락의 프롬프트 합성 및 결과 미리보기 웹앱(MVP). 주요 아키텍처: FE(Next.js/Tailwind), BE(FastAPI), DB(Supabase), 에이전트 파이프라인(Planner→Composer→Runner→Evaluator→Refiner). MVP NFR: 평균 응답 5s 내, 타임아웃 15s, 한국어 톤 일관성, 개인정보 최소 수집 및 전송 암호화.

---

## 3. 코드 품질 원칙
목표: 유지보수성·이해성·일관성 유지

3.1 가독성 및 설계
- 함수/모듈은 단일 책임 원칙(SRP)을 따름.
- 함수 길이는 가능하면 100행 이하 권장. 긴 로직은 작은 유닛으로 분리.
- 의미 있는 이름(예: `composePromptBundle`) 사용. 마법 숫자(문자열) 하드코딩 금지.

3.2 스타일 & 린트
- FE: ESLint + Prettier, 스타일 가이드(예: Airbnb/또는 팀 규칙). BE: Black/ruff(python) 또는 프로젝트 규칙.
- `pre-commit` 훅으로 포맷/린트 자동 실행. CI에서 린트 실패 시 머지 차단.

3.3 의존성 관리
- 외부 패키지 추가는 PR에서 이유(보안·라이선스·용량·대체안)를 명시.
- 의존성은 주기적으로(예: 분기별) 감사.

3.4 코드 리뷰
- 최소 1명 이상의 코드 리뷰 승인 필요(핵심 모듈은 2인 권장).
- 리뷰 체크리스트: 기능 정확성, 에러 핸들링, 보안 영향, 성능 영향, 테스트 포함 여부, 접근성(프론트).

3.5 계량적 규칙(예시)
- 린트 에러: 0
- 심각 보안 취약점: 0
- 함수당 사이클로매틱 복잡도 권장 한계: 10
- PR 변경 라인 권장: <500줄 (초과 시 분할 요청)

## 4. 테스트 표준
목표: 자동화된 테스트로 회귀 방지 및 신뢰성 확보

4.1 테스트 계층
- 단위 테스트: 핵심 비즈니스 로직(Planner, Composer 변환 규칙 등).
- 통합 테스트: BE→DB, Runner→LLM(모킹 또는 스테이징) 연동.
- E2E: 핵심 사용자 흐름(입력→미리보기→피드백) 최소 시나리오.

4.2 커버리지와 품질
- 라인 커버리지는 단독 지표가 아님. 핵심 모듈(예: Planner/Composer/Evaluator) 80% 목표, 전체 프로젝트 목표 60% 권장.
- 테스트는 독립적이고 반복 가능해야 함. 외부 의존성은 가능한 모킹.

4.3 CI 통합
- 모든 PR에서 자동 테스트 통과 필요. 실패 시 머지 차단.
- 플래키(Flaky) 테스트는 태깅하고 24시간 내 조사/수정 우선.

4.4 성능/부하 테스트
- 성능 관련 PR(예: Runner 변경)은 간단한 성능 스모크(벤치)를 포함.
- 스테이징 환경에서 재현 가능한 부하 테스트 실행 및 결과 비교.

4.5 테스트 네이밍과 관례
- 테스트 이름은 기대 동작을 설명: `test_compose_prompt_with_constraints_returns_expected_format`
- Fixture/Factory를 사용해 테스트 준비 코드를 일관되게 유지.

## 5. 사용자 경험(UX) 일관성 원칙
목표: 한국 비즈니스 사용자에게 일관되고 접근성 높은 UX 제공

5.1 디자인 시스템
- 공통 컴포넌트(버튼, 입력, 모달, 알럿)는 디자인 시스템으로 관리(스토리북 권장).
- 색상·간격·타이포그래피 변수 중앙 관리.

5.2 접근성(a11y)
- WCAG 2.1 AA 수준을 목표로 주요 화면 자동 검사 및 수동 확인.
- 키보드 네비게이션, 적절한 ARIA 속성, 포커스 관리 필수.

5.3 톤 & 한국어 품질
- Composer 규칙은 한국 비즈니스 톤(존댓말, 과도 확언 금지)을 반영.
- Evaluator 체크리스트에 톤 일치 항목 포함(존댓말 사용, 문장 수/포맷).

5.4 국제화(i18n)
- 모든 사용자 문자열 리소스 파일로 관리. 하드코딩 문자열 금지.
- 로케일 포맷(날짜/숫자/통화) 적용.

5.5 문서화/디자인 핸드오프
- UI 변경 시 스토리북/디자인 링크(Figma)와 함께 PR에 포함.

## 6. 성능 요구사항
목표: 핵심 사용자 시나리오에서 만족스러운 응답성 제공

6.1 초기 SLO(프로젝트 요구에 맞춰 조정 가능)
- MVP 웹앱(미리보기): 평균 응답 5s 이내, 타임아웃 15s (sketch.md의 NFR 준수).
- API: 핵심 읽기 경로 p95 < 300ms, 복잡 처리 p95 < 1s.

6.2 측정 및 모니터링
- RUM(실제 사용자 모니터링) 및 서버 메트릭(레이턴시, 메모리, CPU) 수집.
- APM/로그로 주요 경로 추적(trace) 설정.

6.3 PR 레벨 성능 검사
- Runner/Prompt 합성 변경 시 경량 벤치 포함(예: 간단한 latency 비교). 스테이징에서 정밀 부하 테스트.
- 성능 회귀(예: p95 10% 이상 악화) 시 병목 분석 및 조치.

6.4 최적화 권장 사항
- 캐시(입력 해시 기반), 토큰 상한, lazy loading, prompt/response 크기 최적화.
